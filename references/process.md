# 过程性规范:可观测性 / 文档 / 分支策略（第八/十/十四章全文）

> 本文件是可选资料，不会随 `dev-standards` 自动生效。
> 只有用户明确要求生产可观测性、完整文档交付或分支/PR 流程时才读取相关小节；普通功能开发不要加载。
> 文中的“必须”仅在用户选定的生产/交付场景内成立，不能覆盖主文件的功能优先与最小实现原则。

---

## 八、可观测性规范

> **作用域:** 仅在用户明确要求生产级可观测性，或已有运行证据表明当前功能需要时使用。真实部署本身不等于必须引入本章全部机制；按已知故障和运维需求选择最小子集。

### 8.1 关键路径必须有指标

计数（请求数 / 成功数 / 失败数）+ 错误时间戳 + 延迟（p50/p95,不用平均值）。

### 8.2 下游依赖必须有保护

- 必须有**超时**设置
- 连续失败超过阈值时必须有**熔断**（快速失败,不继续发请求）
- 熔断恢复要有探测机制（HALF_OPEN 状态）

### 8.3 告警要有冷却时间

同一条告警规则触发后,冷却期内不重复触发,避免告警风暴。

### 8.4 状态可查询

运行时状态必须有查询入口（如 `/status` 命令或健康检查端点）,不能只有"翻日志文件"一种方式。

### 8.5 与最小实现原则的取舍

`/status` 端点 + 结构化日志已覆盖 80% 生产可观测性需求。除非部署环境强制（如 K8s 已有 Prom 抓取）或业务规模超出单机承载（>100 节点）,否则不引入 Prometheus/ELK。

## 十、文档规范

> **作用域:** `CHANGELOG.md` / `CONTRIBUTING.md` 面向**有外部使用者或协作者**且用户要求完整交付的项目。solo 个人项目 / 一次性工具可只维护能支持当前使用的 `README.md`，CHANGELOG 用 commit 历史代替，`CONTRIBUTING.md` 不建。需要知识收尾时再读取 `methodology.md` 的 B.5。

### 10.1 必须维护的文档

| 文档              | 更新时机                           |
| ----------------- | ---------------------------------- |
| `CHANGELOG.md`    | 每次有用户可见的变更               |
| `README.md`       | 安装方式、配置项、使用方法有变化时 |
| `CONTRIBUTING.md` | 开发流程、规范有变化时             |

### 10.2 CHANGELOG 格式

遵循 [Keep a Changelog](https://keepachangelog.com):

- `Added` — 新功能
- `Fixed` — Bug 修复
- `Changed` — 行为变化
- `Removed` — 删除的功能

**不要**直接粘贴 git log,要写**用户视角**的描述。

### 10.3 .gitignore 必须覆盖

- 覆盖率报告（`htmlcov/`、`coverage.xml`）
- 类型检查缓存（`.mypy_cache/`、`.ruff_cache/`）
- 含密钥的配置文件（`.env`,保留 `.env.example`）
- 编辑器专属文件按团队约定:`.idea/` 建议忽略;`.vscode/` 不少项目刻意提交其中的共享配置（调试、推荐扩展）,提交与否保持全仓库一致

### 10.4 项目交付完整性（新建/交付项目时必检）

> **作用域:** 面向**作为独立产物交付**的项目(有用户会安装/使用它)。纯一次性脚本、内部实验片段不适用。

新建或交付一个项目时,其文档/脚本必须覆盖以下五项,任一缺失 = 交付不完整:

| 组件 | 要求 |
| ---- | ---- |
| **安装指令** | 用户 / Agent 如何安装项目及其依赖 |
| **卸载指令** | 如何干净地移除项目 |
| **一键更新** | 更新到最新版本的命令 |
| **面向用户的手动操作指令** | 用户可直接执行的操作命令,清晰、简单、带例子 |
| **面向 Agent 的一键操作指令** | 可无人值守执行、返回结构化结果的全自动命令 |

设计原则:

- **安装/卸载**:必须可逆、干净,不污染系统环境
- **一键更新**:保证版本同步与回滚能力
- **用户指令 vs Agent 指令**:前者面向人类可读,后者面向自动化(结构化输入输出)

## 十四、分支策略

> **作用域:** 仅在用户明确要求设计或执行完整分支/PR 流程时使用。solo 个人项目可在 `main` 直接提交小改动、无需 PR review；不要因为仓库存在 CI 或部署就自动强制整章。任何项目都不主动 push，除非用户明确要求。

### 14.1 分支模型

- 主分支:`main`（受保护,只能通过 PR 合并）
- 功能分支:`feature/<short-name>`（从 main 切出）
- 热修复:`hotfix/<issue-number>`（从 main 切出）
- 实验分支:`experiment/<name>`（从 main 切出,验证后删除或合并）

### 14.2 命名约定

- 功能分支:`feature/add-user-auth`、`feature/refactor-db-layer`
- 修复分支:`fix/42-login-timeout`、`hotfix/89-crash-on-startup`
- 实验分支:`experiment/new-cache-strategy`

### 14.3 PR 规范

- 标题格式:`<type>(<scope>): <subject>`（同提交规范 9.1）
- PR 描述必须包含:
  - 变更摘要（1-3 句）+ 关联 Issue（`Closes #123` / `Relates #123`）+ 测试说明 + UI 截图（UI 变更必附）
- PR 合并前必须通过:pre-commit 全绿 + 全量测试通过 + 至少一轮 review

### 14.4 合并策略

- 功能分支 → `squash and merge`（保持 main 线性历史）
- 热修复 → `merge commit`（保留完整时间线,便于追溯）
- 实验分支 → squash merge 或关闭（不保留实验历史）

### 14.5 生命周期

- 功能分支合并后立即删除
- 超过 7 天未合并的分支,检查是否还相关,不相关则关闭
- 禁止在 main 上直接 push（只能通过 PR）
