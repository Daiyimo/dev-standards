# 附录 D、静态扫描告警的修复规范

> 本文件是可选方法库。仅在用户明确要求处理扫描告警 / 代码质量问题，或拿到一份扫描报告要修时，读取对应小节；不要一次通读并套用全部协议。
> 文中的“必须 / 禁止”只约束被明确选中的修复任务，不自动覆盖主文件的功能优先级与最小实现原则。
> **预防规则在主文件**：第六章（提交前跑一遍项目已有的 lint）与第九章（行宽按字符数、阈值写进项目配置、收窄异常前查异常面、有意的宽捕获要声明、不留死代码）以及完成前最小检查，那些是日常写代码时生效的；本附录只在**报告已经出现**时用。
> 示例以 pylint / Python 为主，方法是通用的：换语言时把“异常面”换成该语言的错误返回约定，把“禁用注释”换成对应抑制机制。D.6~D.10 是行宽、死代码、C/C++ 空指针与 Go 注释类的具体修法。

扫描告警修完分两种结果：**代码变好**，或者**扫描变绿但行为退化**。区分这两者靠的不是规则字面意思，是查清被改动代码原本在容什么错。

## D.1 先对齐基线，再动手

修告警的第一步不是改代码，是确认“这份报告描述的是眼前这份代码”。

0. **先跑 `python scripts/detect.py <路径>`。** 本 skill 自带检测器，不要求使用者先导出扫描报告。确实拿到外部报告时，才需要下面 1~5 条对齐——转存常丢行，曾有一份转存少了最后一条，重新解析原始表才拿到完整条数。

1. **用原始报告，不用二手转存。** 二手 dump / 转贴常常丢行：本次拿到的转存文件少了最后一条（序号 31），直接从原始 xlsx 重新解析才拿到完整的 31 条。报告条数先和原始来源核对一遍。
2. **用行号核对版本。** 告警行号和当前文件逐条对照：对得上，说明扫描后代码没动过，可以放心按行号定位；对不上，先弄清中间有哪几次改动，否则会修到错误的代码上。
3. **反推扫描配置。** 报告里的超长字符数（129 / 128 / 122 / 126 / 127 / 130 / 123）全部超过 120，说明阈值是 `max-line-length=120`；而项目里可能根本没有 pylint 配置文件——配置在扫描平台侧。不反推就会用自己的默认值（79 / 88）误判。
4. **宽度按字符数，不按字节。** 含中文的源文件用 `awk length` 或 `wc` 量会按字节计（UTF-8 中文 3 字节），本次因此多出 4 个假阳性。量宽度用能按字符计的工具（Python `len()`），并和报告给的长度逐条对上。
5. **报告行号定位不到超限行时，把这当成一条发现上报**，不要猜哪一行“大概对应”。版本漂移、转存丢行、只拿到部分源码都会造成错位。如实写“报告列了 N 处，当前代码只能核实 M 处”。

## D.2 收窄异常前，先查被调方的真实异常面

**规则：收窄 `except` 捕获的类型前，必须读被调函数的源码或文档，确认它到底抛什么。查不清就保留宽捕获。**

只看“宽泛不好”就收窄，会把容错边界改窄，而且这种退化不会报错、只会静默改变行为。

本次的真实案例：被调的设备 SDK 在对端返回失败时抛的是**裸 `Exception`**（源码 `raise Exception(message)`），只有网络层才抛 `requests.RequestException`。如果按字面把设备命令调用点的 `except Exception` 收窄成 `except requests.RequestException`：

- 原来：对端失败 → 记 warning → 返回 False → 上层继续跑，主流程照样执行。
- 改后：对端失败 → 裸 `Exception` 不被捕获 → 一路抛到上层批量执行的用例级 catch → **整个用例被判失败，主流程根本没跑**。

一次设备抽静就从“告警后继续”变成“用例失败”，而扫描是全绿的。

**执行方式：** 顺着调用链读被调实现，列出它可能抛出的具体类型（含它自己 `raise` 的裸异常），再决定捕获范围。拿不准的被调方按“会抛宽异常”处理。

## D.3 可收窄 与 有意的宽捕获

不是所有 `except Exception` 都该收窄。先分类：

| 类型 | 判断依据 | 处理 |
| --- | --- | --- |
| 可收窄 | 失败面有限且明确：HTTP 调用、文件读写、subprocess、编解码、JSON 解析、字典查找 | 收窄成具体类型元组 |
| 有意的宽捕获 | 故障隔离边界：单次重试单元、单个任务/用例、顶层兜底；或外部服务 + 自由文本解析 | 保留宽捕获 + 禁用注释 + 一行理由 |

**有意的宽捕获用禁用注释显式声明，不要硬收窄成看似具体的类型：**

```python
except Exception as e:  # pylint: disable=broad-except
```

并在上一行写清理由（为什么这里必须容错、收窄会导致什么）。理由写给下一个读代码的人，不是写给扫描器。

**两个实测约束：**

- `except ( requests.RequestException, Exception)` 这种“半收窄”**仍然会被判 broad-except**——元组里出现 `Exception` 一样报警。所以要么真收窄（不含 `Exception`），要么老实保留宽捕获。
- 禁用注释要写在 `except` 行；规则名用报告里的那个（本次是 `broad-except`）。

## D.4 验证“修复”本身

扫描分数变高不等于修好了。至少做两层验证：

1. **没有引入新告警。** 把修改前后的完整扫描输出**按规则聚合计数**再对比，而不是只看目标规则归零。本次其余 20 类规则计数完全一致，才能说明没有顺手带出新问题。只盯目标规则会漏掉“修 A 引出 B”。
2. **行为没有变。** 扫描告警多数是行为无关的，但异常收窄不是。可用的做法：
   - 对每个改动点灌入真实异常类型，确认仍然被捕获、返回值和改前一致；
   - 需要严格比对时，把修改前后的文件并列加载（stub 掉外部依赖），比纯函数的输出、参数解析结果、`--help` 全文等。

> 这对应主文件第六章“验证手段本身要可信 / 验证者不能自证”：扫描器既是工具也是被验对象，不能它说绿了就当成通过。

## D.5 范围外的告警要显式报告

一次修复通常只覆盖报告里列出的规则。完整扫描往往还有一批本次范围外的告警（本次是约 140 条其他规则，其中 115 条 `logging-fstring-interpolation`）。

- **不静默扩大**：没在要求范围内就不动手改，那属于另一次任务。
- **也不静默忽略**：在汇报里明确说清“还有哪些没处理、多少条、属于什么规则”，让用户知情后决定。
- 用户说“先不处理”是知情后的决定，和你漏掉了是两件事——措辞上要能区分。

## D.6 行宽：按语法边界重排，不按字符数硬折

**只改检测出来且确实超限的行。** 115 字符的行没超 120 就不动——顺手拆了会放大 diff、混淆回归范围，下一轮 review 时无法区分“哪些改动是修告警、哪些是白改的”。

| 反模式 | 正例 |
| --- | --- |
| 把长 dict literal 折成两行但键值仍挤在一行 | 一键一行 |
| 把 `parser.add_argument(...)` 的参数字符串截断 | 一参一行 |
| 为了凑宽度切断字符串字面量 | 字符串保持完整，改折外层结构 |
| 顺手把没超限的行也重排 | 只改超限的行 |

```python
# 前：129 字符
return {"pass": None, "reason": "EXTERNAL_API_KEY not configured", "confidence": 0.0, "verdict": "skip", "analysis": {}}

# 后：一键一行，内容一字未改
return {
    "pass": None,
    "reason": "EXTERNAL_API_KEY not configured",
    "confidence": 0.0,
    "verdict": "skip",
    "analysis": {},
}
```

## D.7 死代码：先分“真死”和“成组计算的一员”

删之前先分清两种：

- **真死**：赋值后全文件无读取 → 直接删。
- **成组计算的一员**：和相邻变量一起算出来、当前只有部分被用 → 保留，因为它表达的是一个判断。实测中某个只赋值不读取的成员被删，而相邻的两个配套判定保留，后来各自成为独立函数。

未使用的导入、不可达分支同理：删掉比留着便宜；删不掉说明它本该被使用。

## D.8 空指针（`BackwardNull`，C/C++）

- 检测器只报**候选**，必须人工确认：检查点和使用点是否在同一条控制流上。检查在分支 A、使用在分支 B 是这类告警的主要来源。
- 修一处，把同一函数的**相邻同类告警一起处理**（报告描述里常带“[N] 行也有相同告警”）。
- 修法是让使用点重新校验，或把检查提到覆盖两条分支的位置——**不是加 `if (x) {}` 空块消告警**。
- 第三方插件、示例代码、vendored 代码同样在扫描范围内。要么修，要么显式申请忽略并留原因。

## D.9 导出符号注释（Go）

按 `standards-registry.md` 第 1 节写。批量补注释时的顺序：先包注释（每个包一处），再按文件聚合补导出符号。补注释时不改任何代码逻辑——这是唯一一类“纯增量”整改，但注释内容必须和实际行为一致，**写错的注释比缺失更贵**。

## D.10 函数规模（≤ 80 行）

超过 80 行时优先按职责拆出 helper，手法见 `ccn-splitting.md`。不要用“删注释、删空行”凑行数——那会让代码更难读，且下一轮加功能时又超限。

## D.11 常见借口

| 借口 | 现实 |
| --- | --- |
| “被调方源码读不到，所以保留宽捕获” | 读不到实现也能判断调用类别：HTTP、文件、subprocess、类型转换的异常面都是已知的。只有该调用确实是“对端失败以裸 Exception 抛出”的边界时才保留宽捕获 |
| “加了 disable 注释就完了” | 没有一行理由的 disable 只是把告警藏起来；下一个读代码的人无法判断它是否仍然必要 |
| “这行 115 字符，顺手也拆了” | 只改检测出来且确实超限的行。预防性重排放大 diff、混淆回归范围 |
| “半收窄更保险” | 元组里出现 `Exception` 一样报 `broad-except` |
| “目标规则归零了，修完了” | 要按规则聚合做前后计数对比，否则看不见“修 A 引出 B” |
| “逻辑等价，不用差分测试” | 逻辑等价是你的判断，差分测试才是证据 |
| “不是我们写的代码，不用管” | 第三方插件、示例代码、vendored 代码同样在扫描范围内。要么修，要么显式申请忽略并留原因 |
| “项目里没有 lint 配置，所以用工具默认值” | 默认值各不相同（pylint 100、flake8 79、black 88），平台阈值可能在项目里根本不可见。反推阈值并写进项目配置 |
