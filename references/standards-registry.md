# 规范注册表

> 本文件是资料库，也是**合并新规范的落点**。加一条规则在这里加一行；加一门语言见 `scripts/detect.py` 的 docstring（新增 `detect_<lang>.py` 并在 `LANG_SUFFIXES` 登记后缀），不需要改主流程。
> 所有阈值与规则名来自对真实扫描表的逐条统计，已脱敏：不含处理人、entityId、内部绝对路径与真实凭据。

## 1. 规则注册表

| 规则名 | 语言 | 阈值 / 要求 | 检测方式 | 可靠度 |
| --- | --- | --- | --- | --- |
| `line-too-long` | Python | 单行 ≤ 120 字符 | pylint，按字符数计 | 可靠 |
| `tosa/linelength` | Go / C++ | 单行 ≤ 120 字符 | `detect.py` 内置，按字符数计 | 可靠 |
| `golint/fnsize` | Go / C++ | 函数体 ≤ 80 行（含注释与空行） | `detect.py` 内置 | Go 可靠；C++ 启发式 |
| `broad-except` | Python | 不收裸 `Exception` | pylint（规则名已归一化） | 可靠 |
| `unused-variable` | Python | 无只赋值不读取的变量 | pylint | 可靠 |
| `unused-import` | Python | 无未使用导入 | pylint | 可靠 |
| `ccn` | Python | 单函数 McCabe CCN，≥40 高 / 20~39 中 | `detect.py` 内置 AST | 与平台偏差 1~2 点 |
| `golint/package` | Go | 每包一处包注释 | `detect.py` 内置 | 可靠 |
| `golint/funccomment` | Go | 导出函数有注释 | `detect.py` 内置 | 可靠 |
| `golint/structcomment` | Go | 导出结构体有注释 | `detect.py` 内置 | 可靠 |
| `golint/interfacecomment` | Go | 导出接口有注释 | `detect.py` 内置 | 可靠 |
| `golint/varcomment` | Go | 导出变量/常量有注释 | `detect.py` 内置 | 可靠 |
| `BackwardNull` | C/C++ | 空检查之后的解引用须重新校验 | `detect.py` 内置窄模式 | **候选，必须人工确认** |
| `error` | 全部 | 源文件读不了或解析失败 | 各检测器自报 | 可靠；**不是某条规范**，是"没查成"的信号，见下方说明 |

**阈值在扫描平台侧，项目里通常看不见。** 表里超长行的实际长度全部越过 120，而项目内可能根本没有对应配置文件。不把阈值写进项目配置（`.pylintrc` / `pyproject.toml` / `revive.toml` / `.editorconfig`），下次改完还是会踩线。

## 2. `error`：不是规范，是"没查成"的信号

三个检测器都会在**源文件读不了或解析失败**时产出 `error` 规则（Python 侧还把 pylint 的
`E0001` 语法错误归到这里）。它不是第 1 节里任何一条规范，但必须可筛、可数：

- 没有它，"这个文件根本没查"会和"这个文件查过了没问题"输出同一份空结果；
- 用 `--rules` 筛具体规范时它会被一起滤掉，想看"有没有文件没查成"就单独跑
  `--rules error`；
- 它是退出码 1 的合法来源之一——只有 `error` 时退出码也是 1。

## 3. 检测能力边界（如实说明）

`scripts/detect.py` 不假装全覆盖。用之前知道它不查什么：

| 检测器 | 覆盖 | 不覆盖 / 已知边界 |
| --- | --- | --- |
| `detect_python.py` | 行宽、宽异常、未使用变量/导入、CCN | 依赖 pylint 已安装；装不上时自动退回内置 AST 检测（只剩行宽 + CCN）。缺 docstring 不在本规范范围内 |
| `detect_go.py` | 包注释、导出符号注释、行宽、函数规模 | **轻量行扫描器，不是 Go 解析器**。假设代码经过 gofmt（声明与右花括号在行首）。不理解 struct tag、cgo、build tag 里的花括号。项目有 golangci-lint / revive 时以它们为准 |
| `detect_cpp.py` | 行宽、函数规模、`BackwardNull` 候选 | 真正的空指针分析需要 clang-tidy。`BackwardNull` 只报"指针判空后在判空分支之外被解引用"这一种窄模式，**已排除"判空后提前返回"这一安全惯用法**，宁可漏报不误报。**跨行字符串会破坏花括号深度**：`scan_lines` 的 `in_string` 是每行局部变量、不跨行延续，于是 C++11 raw string `R"(...)"` 和普通反斜杠续行字符串都会让深度失真（实测前者报出 phantom 函数，后者把 5 行函数截成 3 行） |

C/C++ 的函数规模检测按"函数签名首行到配套右花括号"计，能识别定义在命名空间或类内的函数（命名空间 / class / struct 体本身不算函数）。

## 4. 从扫描表读出的过程性结论

这些不是某条规则，是真实扫描表共同暴露的工作方式问题：

1. **告警跨轮次累积。** "首次发现"标签显示同一批告警来自第 2、3、15、26、67 轮等多个扫描轮次——被反复报了多轮，因为始终没修。修完的标准是下一轮不再出现，不是本轮关单。
2. **老代码不会自动过期。** 表里最早的问题提交时间是四年前，至今仍是"待修复"。风险表是累积视图，不会因为你没看就消失。
3. **定级和修复成本不成正比。** 一份 139 条的 Go 报告里 126 条"严重"全是导出符号注释（最便宜的一类），13 条"一般"才是行宽和函数规模。排期按"成本 / 收益"排，不要按严重度排。
4. **报告条数会骗人。** 139 条的 Go 报告里真正的行为风险是 0 条（全是注释与格式）；7 条的 C++ 报告里每条都是空指针。修之前先按规则分类，再决定批次。
5. **规则 ID 会随工具版本漂移。** pylint 2.x 的 `broad-except`（W0703）在 3.x/4.x 改名 `broad-exception-caught`（W0718）。写死任何一个都会在换版本时失效——`detect_python.py` 因此按符号名做归一化，而不是按 ID 匹配。
6. **范围外的违规要显式报告。** 一次修复通常只覆盖要求范围内的规则。没动的部分要说清"还有哪些、多少条、什么规则"，让使用者知情后决定；不静默扩大，也不静默忽略。
7. **脱敏是提交前动作。** 测试数据文件里的真实账号口令必须替换成占位符（`<your-account>` 形式）；运行产物、缓存、`.env`、`__pycache__` 不进入版本库。

## 5. 与外部工具并存

项目里已有 golangci-lint / revive / clang-tidy / 其他分析器时：

- **以项目工具为准**，`scripts/` 下的检测器是未装工具时的回退，不是替代品。
- 规则名不一致时，在本文件第 1 节加一张映射表，不要改检测器去迎合某一个工具的命名。
- 两套都跑、结果合并时，按规则名去重后再计数，避免同一处违规被算两次。

## 6. 实测终态（校准依据）

一条规则的"正确终态"不是 0 条。以 Python 宽异常为例，实测 23 处的正确处置是：

- 13 处收窄成具体类型元组（失败面有限且明确）；
- 10 处保留宽捕获，逐处加 `# pylint: disable=broad-except` 并在上一行写理由。

清零宽捕获本身不是目标；**该收窄的收窄、该声明的声明**才是。行宽同理：7 处超长行全部按语法边界重排后，超限行数为 0，但这不是"把所有行都重排"。
